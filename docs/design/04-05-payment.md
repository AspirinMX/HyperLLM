# HyperLLM Phase 2.7 支付、兑换码与资源包购买

设计已确认，待实现。依赖[账务与投影链路](./04-04-settlement-pipeline.md)。

## 1. 首版范围

Stripe 以 USD 收款，支付宝和微信支付以 CNY 收款。三家直连，每个环境每渠道配置一个商户。充值订单只发现金，资源包订单只发一个资源包。兑换码核销只发赠金。所有发放沿用 `cdc.billing` 和现有发放授权、折叠及投影流程。

| 渠道 | 支付产品 | 下单响应的支付指令 |
| :--- | :--- | :--- |
| Stripe | 一次性 Checkout，USD | 收银台跳转 URL |
| 支付宝 | 电脑网站支付，CNY | 支付宝签名表单的目标和字段 |
| 微信支付 | API v3 Native，CNY | 原样返回 `code_url` 作为二维码内容 |

浏览器回跳展示订单查询结果。Stripe 的履约条件检查已付款状态。微信支付的二维码有效期和订单关单分别处理。渠道接口依据 [Stripe Checkout 履约](https://docs.stripe.com/payments/checkout/fulfillment)、[支付宝网站支付](https://aipay.alipay.com/article/3241) 和 [微信 Native 支付](https://pay.weixin.qq.com/doc/v3/merchant/4054257695)。

## 2. 下单与订单查询

- `console` 提供 `POST /api/v1/orgs/{orgId}/payment-orders`、订单列表及详情。按现有租户权限校验组织归属。下单限 `OWNER` 和 `BILLING`。查询按组织账单读取权限。
- 充值输入包括渠道和支付币种的最小单位金额。买包输入包括渠道与已上架的 SKU。服务端从 SKU 生成价款和权益快照。快照记录 SKU 版本、名称、单位类型、总量、适用模型与有效期。有效期从渠道确认的付款时间起算。
- 运营配置平台汇率，语义为每一单位原币兑换的 USD。美元汇率固定为 `1`。订单持久化 `pay_amount_minor`、币种、汇率、充值的 `credit_micros` 或资源包规格。同一配置版本的汇率舍入至存储精度再参与计算。金额运算以整数与十进制换算完成。
- 美分与分的转换公式为 `credit_micros = ceil(pay_amount_minor × 10_000 × fx_rate)`。资源包以 micro-USD 定价，支付金额为 `ceil(sku_price_micros / (10_000 × fx_rate))`，按渠道校验可收款范围，微美元和批次单位满足 Lua 精确整数上限。包订单的 `credit_micros` 为零。已经提交的订单沿用原快照。
- 每次创建要求 `Idempotency-Key`。通过 common 的 `@Idempotent` 护住重复请求，数据库按组织、操作和请求键保持唯一，并比较标准化请求指纹。同键异参返回 `409`。鉴权先于可重放结果读取，复用请求结果时按当前权限返回订单。Redis 幂等记录到期后仍可找到原订单。
- 本地订单先提交，再用稳定的商户订单号与渠道幂等键创建支付。遇到超时按原订单号查单或重试，截止前沿用原报价。渠道网络调用在 PostgreSQL 事务之外执行。独立记录创建返回的渠道引用和最终交易号。支付数据仅通过租户鉴权接口返回。
- 订单查询同时返回 `paymentStatus` 与 `fulfillmentStatus`。已付款事务携带持久的 `eventId` 与 `occurredAt`。账本精确确认前显示 `PENDING`，折叠后显示 `APPLIED`。通过 ledger 按事件身份判定确认，outbox 清理后仍可查询。

## 3. 确认收款与发放

`console` 的渠道 Adapter 统一返回支付指令、查单结果与经过校验的支付通知。Adapter 处理渠道协议、签名、交易生命周期和响应确认。订单模块持有交易匹配、关单条件、状态迁移和履约授权规则。Webhook 与主动查单共用同一个确认入口。可信回调在验签及交易字段校验后，以渠道和通知身份调用 common 的 `@Idempotent`。幂等缓存失效时由订单状态和数据库约束继续防重。

1. 验证渠道签名及商户或应用身份。Stripe 对原始 body 验签。微信验签后解密通知。支付宝按签名参数验签。随后校验最终收款状态、订单号、渠道交易号、实付币种及最小单位金额。异常通知只记录必要的订单标识和校验失败类别。页面回跳参数只用于定位订单。
2. 充值订单发出支付指令前，在钱包行锁下预留可发放容量。现有现金余额与生命周期计数、未确认 outbox 充值、待支付预留共用同一容量检查。人工充值也计入待支付预留。订单授权时原子消费这份预留并写出 outbox，两个阶段只占一次容量。
3. 确认收款事务按统一锁顺序获取钱包与订单，复核旧状态并保存唯一渠道交易号。订单更新为 `PAID`，同时写一条 `RECHARGE` 或 `PACK_GRANT` 授权并保存事件身份。订单状态、交易唯一约束和 outbox 提交共同防止重复发放。以渠道确认的金额和订单中锁定的履约参数为准。
4. 提交后返回渠道要求的成功应答。有效通知重复送达时返回成功。可重试异常交由渠道重试和查单作业。主动查单匹配到成功交易时复用确认事务。到期后先查单或关单，渠道确认未收款且不可继续支付后释放容量。回调到达时间晚于本地截止时间的已收款订单仍进入确认流程。
5. 有可信收款证据但凭据与订单不匹配，或渠道状态相互矛盾时，持久化待处理异常并告警。退款、拒付与渠道异常在 `admin` 关联原订单和原有履约记录，运营核对已消费金额与残余权益后记录处理结果。原充值和入账流水继续用于追踪。

### 3.1 发放事件与镜像

- 在现有 `BillingMoneyEvent` 中增加带类型的发放详情。现金充值和买包携带订单引用。券赠金携带券与兑换记录引用、模型和到期时间。买包事件携带批次 ID、单位类型、总量、适用模型与到期时间。事件 ID 与发放时间落在业务记录上，重放保持原值。
- 消费者持钱包行锁，以账本事件身份去重，写 `wallet_ledger.ref_order_id`，并插入实际权益批次。`PACK_GRANT` 作为独立账本类型，`pack_delta_units` 为正，现金及赠金 delta 为零。发放 Lua 在存活镜像上同步添加相应批次索引、item 和幂等标记。冷租户由已折叠的快照加载。多模型包的索引属于同一个批次，一次原子投影完成。
- 发放处理晚于权益到期时保留发放与到期的账务证据，折叠所得可用额为零。投影校验缺失结构、镜像版本和批次有效期。SQL 事务回滚后的重放复用钱包内的事件幂等标记。

## 4. 运营与兑换码

- `admin` 支持资源包 SKU 上下架和价格、模型范围、有效期配置。每个已下单 SKU 的真实规格保存在订单。修改或下架影响后续下单。
- 运营创建券模板、批量生成兑换码、暂停活动和作废未使用码。出码时锁定面额、适用模型与有效期。更新条款时新建模板。码明文仅在批次创建时交付，落库只留 HMAC 和脱敏提示。批次幂等记录重放仅返回批次状态与元数据。
- `console` 提供 `POST /api/v1/orgs/{orgId}/redemptions`。核销方限组织的 `OWNER` 和 `BILLING`。事务先锁券模板，检查状态及活动总次数、每组织次数，再条件消费未核销且未过期的码，在同一事务内保存事件身份、写赠金授权。已核销码按原组织重放结果，其他组织只能收到通用不可兑换响应。
- 核销返回 `202` 与事件 ID。同一码、不同码共享限额、模板暂停与核销并发，均由数据库状态和锁约束。通用请求幂等用于阻止重复提交，数据库事务用于约束最终发放次数。

## 5. 迁移与验收

用新的 Flyway 版本追加 SKU、支付引用与容量预留、兑换持久身份及必要的支付异常记录。同步更新账本类型并生成 jOOQ。发布顺序为数据库迁移、可读取兼容事件的消费者、生产者和通道开关。

| 场景 | 验收结果 |
| :--- | :--- |
| 三渠道创建订单、成功回调、查单补偿 | 一笔收款产生一条授权、一笔折叠及一次投影，查询经过待入账到已入账 |
| 签名失败、商户不符、币种或金额不符 | 无发放。可信但不匹配的收款证据产生待处理记录 |
| 回调与关单并发、回调丢失、重复交易号、跨实例重试 | 以渠道终态为准，容量只释放或转化一次，交易号只绑定一个订单 |
| 同键异参、回放缓存失效、outbox 已清理 | 异参冲突，原始应用结果仍可查询 |
| 并发下单与人工充值、订单过期 | 容量以钱包行锁串行扣占，过期释放依赖渠道终态 |
| 兑换码并发、同券多码并发、赠金与包冷加载 | 总量和组织次数守住上限，批次只发一次，模型限制与到期语义一致 |

测试基线为渠道沙箱或等价测试模式，以及可重复的签名模拟集成测试。渠道账号与产品开通状态单独登记，验收报告逐渠道标明实际跑过的验证。

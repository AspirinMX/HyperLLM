# HyperLLM Phase 2.9 ClickHouse 摄入、用量与毛利

已实现。依赖[结算事件与 Redis 权威层](./04-04-settlement-pipeline.md)。资源包销售额读取 [支付订单](./04-05-payment.md)。

> **实现登记**：`admin` 的请求事件消费者按 Kafka 分区/offset 批写 `llm_request_events`，ClickHouse 成功后在同一 PostgreSQL 事务推进 `analytics_ingest_positions` 并标记 `analytics_hours`；汇总任务按已提交位置去重后写入带版本的 `usage_hourly`，写入 `usage_hourly_published` 后共享查询才会选中。控制面 API 为 `GET /api/v1/orgs/{orgId}/usage` 与 `GET /api/v1/admin/analytics/{margin,pack-sales,rejects}`。

## 1. 数据源与口径

`llm.request.events` 持续由网关直投 Kafka。每个已准入的客户端调用产生一条终态请求事实，含服务端生成的稳定 `requestId`。失败尝试与渠道切换汇进同一个请求的结果。Kafka 复制、重投与消费重试保留请求身份。报表反映已收到的请求事实，展示摄入进度及计量覆盖范围。资金与预算折叠走独立的结算管道。

| 指标 | 口径 |
| :--- | :--- |
| 请求量、成功率、延迟、用量 | 按去重后的终态请求聚合。TTFT 只统计获得首字节的请求。各 token 类别保留协议规范化的用量 |
| 请求总价、现金实扣、赠金实扣、包用量 | 请求总价取当前请求的定价快照。实扣取结算结果。按单位类型展示 Token 包与次数包的用量 |
| 上游采购成本 | 以分派时的渠道采购价和可取得的上游用量计量。保留每次尝试的渠道、已计量成本和计量依据，记录未知尝试数 |
| 请求现金贡献 | 现金实扣减已计量上游成本。现金实扣为正时可算贡献率。成本覆盖不完整时显示相应标记 |
| 资源包销售 | 从 PostgreSQL 按订单付款时间与锁定汇率统计实际收款，退款、拒付单独列示。报告中展示原币金额与 micro-USD 换算额 |

包覆盖的请求仍展示实耗单位与已计量采购成本。请求现金贡献只采用该请求的现金实扣为收入口径。资金对账使用 2.6 的账本与逐笔证据。采购成本、现金贡献、赠金和包销售的汇总内部使用足够精度的整数运算，并检查返回的 micro-USD 范围。

生产者从结算结果补齐包抵扣单位、单位类型和必要状态。渠道成本未知时保留未知标记，避免用 0 补齐。标识、时间、模型、渠道、协议、状态、计量与费用采用字段白名单。Prompt、Completion、工具参数、请求响应头、原始上游错误与认证凭证保留在对应请求的内存生命周期内。

## 2. 摄入与去重

1. `admin` 配置独立的报表消费组、执行池和 ClickHouse 连接池，向按事件月份分区的 `llm_request_events` 批写事实。事实表带 Kafka 分区与 offset，保留 365 天。摄入端校验 Kafka 结构和允许的字段类型。拒收记录保留来源位置、身份和错误类别。
2. ClickHouse 成功写入后，在报表控制数据事务中推进该分区已处理的连续位点，并标记受影响的 UTC 小时待汇总。完成这两步再提交 Kafka offset。失败保留 offset 并重试。ClickHouse 不可用时，报表消费组独立积压。
3. 事实读取按已处理位点截取，并按 `(orgId, requestId)` 选取唯一事实。请求的归属、时间和用量随同一身份保持一致。多批插入、合并前后及新 offset 上的重投都由这一步去重。同一身份内容冲突时记录数据异常，保留定义的首个有效事实。

现有增量物化视图会直接汇总新插入的数据块。[ClickHouse 增量物化视图文档](https://clickhouse.com/docs/materialized-view/incremental-materialized-view)。小时物化结果改由下节的去重后任务发布。

## 3. 小时汇总与查询

1. 汇总任务取待重算小时与各分区已处理的连续位点，按组织、项目、Key、虚拟模型、渠道和小时聚合去重事实。延迟分位数保留可合并状态，查询时合并分组状态。金额、数量和 token 直接汇总。请求量、实耗及现金实扣归请求最终渠道，采购成本各归实际尝试渠道。仅发生重试成本的分组不增加请求量。
2. `mv_usage_hourly` 保存小时级物化结果。一次重算为该小时产生一个版本。整批结果完成后发布该版本与位点快照，查询仅取已发布版本。计算期间新到的事实保持待处理标记。重复重算与旧任务交错时，以已发布的进度控制版本推进。
3. 晚到或回放的请求按原事件小时标记重算。健康时以新用量 2 分钟内可查为目标，超时展示报表延迟。聚合与明细使用同一发布位点核对。同一请求在原始事实和聚合只贡献一次。
4. `console` 的组织用量查询提供时间范围以及项目、Key、模型维度的筛选与分组。组织角色、项目成员范围由服务端解析，组织与项目过滤下沉至 SQL。`admin` 毛利查询按渠道、模型、组织和时段提供请求现金贡献与成本，另带资源包销售数据。分页、范围和分组列均由接口校验。
5. 发布落库结构时使用可重跑的 ClickHouse DDL，覆盖已有 Compose 数据卷。切换到新汇总流程时从保留的事实和 Kafka 位置重建，并以新的版本结果为查询起点。老的增量累加视图在切换时停用。

## 4. 验收

- 对同一身份重复写入不同批次及不同 offset，测试尚未发生后台合并时的请求量、费用和分位数。注入写入成功、位点推进失败，验证重启重投后同样准确。
- 制造晚到事件、小时跨界、汇总写入中断和并发重算。按同一发布位点比对明细与聚合。健康条件下检查 2 分钟时效目标。
- 用包含资源包、赠金、现金、多渠道重试和未知成本的请求校验报表口径。验证包销售时间、订单汇率与渠道退款或拒付记录。
- 用两个租户及不同项目权限验证查询隔离。以可识别的 Prompt、Completion 和上游错误文本做测试，检查 Kafka、ClickHouse 以及摄入错误持久记录符合 ZDR。

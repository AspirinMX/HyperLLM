# HyperLLM Phase 2.8 四层限流与项目预算

滚动窗口、渠道容量与项目月度预算均已实现。依赖[Redis 预占与账务链路](./04-04-settlement-pipeline.md)。

> **实现登记**：项目预算与钱包预占在同一个 `prehold_admit.lua` 内冻结（`gw:budget:proj:{projectId}:{month}`），结算在同一终态脚本里把冻结转成已用；`project_budget_months` 是 Redis 重启后的可证下界。无法证明的月份返回 `503 PROJECT_BUDGET_UNAVAILABLE`，不按 0 补齐。

## 1. 四层限流

| 层级 | 准入判断 | 统计身份 |
| :--- | :--- | :--- |
| API Key | 最近 60 秒 RPM、TPM，以及并发 | 一次已准入的客户端请求 |
| Project | 最近 60 秒 RPM、TPM、既有并发配置，以及月度预算 | 一次已准入的客户端请求 |
| Organization | 组织并发上限 | 一次请求租约，覆盖流式调用 |
| Upstream Channel | 渠道的 RPM、TPM 和并发容量 | 一次获得发起资格的上游尝试 |

### 1.1 租户侧窗口与并发

- 窗口按 Redis 时间计算，取 `(now − 60s, now]`。只为启用的限制维护时间有序的成员及累积值。以 hold ID 去重，Lua 逐出过期成员后检查两层额度。成功准入在同一 Lua 写入速率、并发租约、钱包和项目预算预占。准入拒绝保持各项使用计数不变。
- API Key 和 Project 的 TPM 用估算的输入量与请求输出上限保留额度。请求结束时仅对仍在原窗口内的成员按已获得的实际 token 校正，重复收尾最多校正一次。无可信用量时保留估算。缓存及推理 token 按协议的规范化用量计算，避免重复加入总量。
- 并发按活跃租约成员计算。心跳按 hold ID 延长自己的租约，结束或回收按同一 ID 释放。懒清理和后台回收处理到期成员，单个请求的租约到期不影响同行的长流。
- 速率拒绝返回协议对应的 `429`，`Retry-After` 根据足以释放额度的窗口位置或并发租约估算。API Key 与 Project 的上游切换复用同一客户端预占。

### 1.2 渠道容量

渠道 Adapter 在每次上游分派前调用容量模块。容量模块按 `channelId` 做原子的窗口与租约检查，一条上游尝试使用独立 attempt ID。多个组织和路由到同一 Channel 共享同一额度。单 Redis 部署内使用独立键空间，后续按组织分 cell 时各 cell 继续访问同一个 Channel 容量权威。

候选渠道容量不足时尝试其他合格渠道，全部健康候选均无容量时返回 `429 CHANNEL_CAPACITY_EXCEEDED`。发起尝试的 RPM/TPM 独立计数，失败释放尝试的并发租约。渠道 TPM 在 60 秒内保守保留分派估算，以保护上游账号。流式尝试以心跳保持租约，首帧前失败后的下一次尝试重新获取渠道容量。

## 2. 项目月度预算

### 2.1 归属与额度语义

- 预算以 UTC 自然月核算，归属取首次准入时的 Redis 时间。跨月请求继续结算到原月。金额以适用协议价、折扣后的请求用量总价计算，包含资源包和赠金覆盖的价值。充值、兑换或买包是组织侧交易，项目计量发生在请求使用时。
- 记录月内已用额和在途预占。对于设有硬预算的项目，仅在 `used + held + estimatedUpperBound <= hardCap` 时准入。项目预算上限的修改沿用配置 CDC 与 Redis 刷新，降低上限从下一次准入起生效。
- 预算硬上限控制准入。正常结算记实际用量价值并释放预占。可信用量高于估算上限时按实记录超额，后续请求受硬上限拦截。在途请求按原生命周期收尾，钱包仍按现有分摊及短缺规则处理。
- 撤销未交付预占只释放预算。已交付租约超时回收按原 prompt 兜底价值计入预算。预算费用以既有定价快照及结算的计量结果为准，钱包实际扣款仍以原子应用的 delta 为准。
- 软预算观察已用额并触发告警。硬预算拒绝返回 `429 PROJECT_BUDGET_EXCEEDED`，记录供告警消费的拒绝证据。上限为空表示对应限制未配置。启用计量的初始月发布统计起点，从下一个自然月起覆盖整月。

### 2.2 事件及重建

1. hold 记录项目、预算归属月、冻结金额和 prompt 兜底报价。结算、释放、回收通过既有终态原语原子调节预算已用与冻结。预算和钱包复用同一个 hold 终态和事件 ID。月内预算及待确认索引保持可用，月结束且在途租约与待确认事件清空后清理预算键。
2. 在消费事件增加预算月及实际计量金额。即使钱包三桶 delta 为零，有预算增量也必须产生带原事件身份的结算记录。消费者与 L3 修复在相同账本事务按事件去重，并折叠 PostgreSQL 的项目月度已确认用量。金额分录与预算字段分别记账。L4 按既有规则认亏。工单索引保留项目和预算月。认亏事务以原事件身份折叠可核实的预算值。缺少确切金额时，持久化该项目月的待核实状态。
3. 保存已启用项目月的初始化标记和计量起点。冷初始化或重建走限量、可合并的非 Netty 回源，先验证 Redis 主节点连续性与未确认事件，再核对 PG 边界和活动 hold。原子安装复核权威代际、折叠下界和待确认事件，再写入仍缺失的月状态。检查 PG 折叠位置时使用逐笔确认及版本界限，Kafka 最大 UUID 水位仅供观察。
4. 对 Redis 重启、故障切换或状态缺失建立预算权威代际与重建门禁。只有能证明完整的已确认用量、在途实扣和活动冻结时才安装月状态。未知月份保持待核实状态，命中的硬预算项目返回 `503 PROJECT_BUDGET_UNAVAILABLE` 及重试提示。全量 Redis 状态丢失且影响无法定位到单项目时，受影响月份内启用硬预算的项目都属于待核实范围。未受影响的项目按各自状态准入。
5. `console` 展示已用、冻结、可用、额度和统计起点，标明实时值或已确认值。软预算与硬预算告警依照 [告警设计](./04-08-alerts-reconcile.md)。

### 2.3 接口与发布

在既有项目管理界面对应的 HTTP 接口补全软硬预算与显示字段。预算状态与普通钱包冷加载分别判定，存活钱包继续应用既有 ledger lag 规则。网关热路径使用 Redis，PG 存放预算折叠及初始化证据。实际启用前先发布兼容旧消息的消费者和创建预算存储的迁移，所有网关升级至兼容事件契约后再按统一时间启用计量与限制。

## 3. 验收

- 测试 API Key/Project 同一分钟与跨分钟窗口、跨实例并发、按实归还、上游用量超估和长流超出窗口。验证拒绝请求无速率、钱包或预算预占副作用。
- 测试不同租户竞争同一渠道、单次请求回退多个渠道、并发成员独立心跳和清理。检查 OpenAI 与 Anthropic 的错误形状及重试提示。
- 并发卡在硬预算边界时仅允许可覆盖的预占。验证包与券覆盖、纯预算事件、失败释放、已交付回收和跨月收尾。重复投递、L3 修复及 L4 认亏后逐项核对预算状态。
- 模拟镜像丢失、待确认事件与版本变化，验证可证重建和仅受影响硬预算项目返回 503。核实首次启用的统计起点及后续月切换。
